## 4. Tuning Decisions & Measurements That Led to Each

### 4.1 Option H & Option A1 — `SEARCH_ANN_RANDOM_PAGE_COST = 1.1` & `ExactSearchSQL` Filter Pushdown (`advisor-dec-348`, `advisor-dec-349`)

- **Symptom in R1 (`41563156208`) and R2 (`41567750625`):**
  - `item/medium_colocated` (`R = 0.0044`, `U = 89.60%`, `B p95 = 81.70 ms`) and `item/medium` (`R = 0.6123`, `U = 27.80%`, `B p95 = 80.92 ms`) failed C2, with the report printing `"NOT HNSW: 2 embedding scans: the tenant partition was not pruned to a single scan"`.
- **Root-cause diagnosis (`c2-prune-diag.md`):**
  1. **Harness bugs (Option H, commit `76ef8cb`):** PostgreSQL pruned 15 of 16 partitions in every cell. `ParseANNPlan` (`report.go`) matched both `Bitmap Heap Scan on item_embedding_g1_p6` and its child `Bitmap Index Scan on item_embedding_g1_p6_pkey` because the index name also contained `"_embedding_g"`, falsely reporting 2 scans. Meanwhile, `RunC2` (`runner.go`) ran `ANNPlanEvidence` only on `jobs[0]` (`t2`, `4,000` items, which took the `exact` path), masking non-HNSW plans on `t6` (`50k` items in `_p10`).
  2. **Planner cost inversion from out-of-line TOAST storage (Option A1, commits `fdecca1`, `0b875e1`, `573563b`):** Each `vector(1024)` is `4,104 B` (`> TOAST_TUPLE_THRESHOLD`), so PostgreSQL stores `embedding` out-of-line in TOAST (`96.4%` of table bytes). Main heap fork `rel->pages` holds `~40` rows/page (`2,980` pages for `119,593` rows in `item_embedding_g1_p6`), whereas HNSW stores the vector inline at `1` row/page (`119,594` pages). PostgreSQL's `cost_bitmap_heap_scan` and `cost_seqscan` price only `rel->pages` and charge **zero I/O for TOAST detoasting**, whereas `pgvector` 0.8.6's `hnswcostestimate` TOAST discount (`if (startupPages > rel->pages && ratio < 0.5)`) never fires on item partitions where `rel->pages (1,380..3,236) >= startupPages (985 at ef=64)`. Under default `random_page_cost = 4.0`, HNSW `Limit 20` cost (`3,723–5,576`) exceeded `Bitmap/SeqScan + Sort` (`3,439–3,897`) for `t3` (`6k`), `t4` (`12k`), and `t6` (`50k`), causing the planner to pick full-tenant TOAST scans that timed out at `80 ms`.
- **Changes shipped:**
  - `store/ann.go` (`0b875e1`): Added `SET LOCAL random_page_cost = 1.1` to the read-only ANN `pgx.Batch` via `SEARCH_ANN_RANDOM_PAGE_COST` (default `1.1`, valid range `0.5..4.0`, `off` or `0` omits the statement; forwarded in `infra/docker-compose.yml` and `.env.example` in `573563b`).
  - `store/exact.go` (`fdecca1`): Pushed `(embedding <=> $2) AS dist` and `WHERE 1 - (embedding <=> $2) >= $3` inside the `MATERIALIZED` CTE `tenant_vecs` before joining `item`/`tag`.
- **Measured verification in R3 (`41573086071`):**
  - Every ANN-entering tenant (`t0..t7`, item and tag) chose `Index Scan using <part>_hnsw` at `ef=40` and `ef=64`.
  - `item/medium` improved from `R = 0.6123`, `U = 27.80%`, `B p95 = 80.92 ms` (R2) to **`R = 1.0000`, `Q = 100.00%`, `U = 1.00%`, `B p95 = 66.90 ms` (`ANN-only p95 = 29.86 ms`) — PASS**.

### 4.2 Option L1 — `SEARCH_LEXICAL_FORCE_CUSTOM_PLAN` Default `on` (`advisor-dec-350`)

- **Symptom in R2 (`41567750625`):**
  - R2's FU-SL-1 diagnostic showed that under `force_generic_plan`, prepared lexical statements took `596.8–626.4 ms` on `whale/item/fuzzy` (vs `3.57–12.53 ms` custom) because a generic plan cannot use `text_pattern_ops` B-tree prefix indexes or prune `$3::bool` and scans all `100k` tenant items in `item_user_name_trgm`. It was hypothesized that `pgx` statement caching (`plan_cache_mode = auto`) switched to generic plans after 5 executions and caused C1-L's `94.81 ms` p95.
- **Change shipped (`3dffc74`):**
  - Added `SET LOCAL plan_cache_mode = force_custom_plan` to the lexical read-only transaction in `apps/api/internal/suggest/lexical.go`, controlled by `SEARCH_LEXICAL_FORCE_CUSTOM_PLAN` (default `on`/empty; `off`/`false`/`0` skips).
- **Measured verification in R4 (`41575503986`):**
  - **Harmless, kept as a permanent guard against generic-plan fallback, but did NOT fix C1-L:** R4 measured `C1-L p95 = 93.82 ms` (vs `94.81 ms` in R2) and `c=1` `p95 = 56.25 ms` (`640/2200` item partials vs `676/2200` in R2). Subsequent diagnosis (`c1l-diag.md`) proved PostgreSQL's `choose_custom_plan` was already rejecting the generic plan in R1–R3 because the generic plan cost (`> 5,000`) was far higher than the average custom plan cost (`~600–1,200`).

### 4.3 Option O1b — Vector Search Knob Defaults `250 / 3000 / 3000` (`advisor-dec-352`)

- **Symptom in R3 (`41573086071`) and R4 (`41575503986`):**
  - With A1 active, `item/medium_colocated` still failed at the old default `ef64_scan20000_exact5000` (`R = 0.5556` in R3 / `0.5867` in R4, `U = 40.00%` / `37.20%`, `B p95 = 81.02 ms`, `219/500` timeouts), and `item/medium` had `5–6/500` (`1.00%–1.20%`) timeouts on exact-path tenant `t2` (`4,000` items).

### 4.4 Option L2-B — Tiered Prefix-First `UNION ALL` Lexical SQL (`advisor-dec-353`)

- **Symptom in R1–R5:**
  - `C1-L` failed with `p95 = 93.82–98.09 ms` at `c=8` (`p50 = 65.09–67.25 ms`, `partials = 2452–2556 / 4000` [`61.5%`]) and `p95 = 56.25–56.84 ms` at `c=1` (`partials = 577–618 / 2000` [`29.1%`]), while `C1-H` was invalid due to `27–194 / 4000` degraded semantic requests caused by lexical CPU/pool contention.
- **Root-cause diagnosis (`c1l-diag.md`):**
  - `999 / 1,000` C1-L queries are `mode = "full"` (`fuzzy = true`), and **`460 / 1,000` (`46.0%`)** have `len_runes(qn) ∈ {2, 3, 4}` (`3, 4, or 5` trigrams).
  - At `pg_trgm.similarity_threshold = 0.35`, `gin_trgm_consistent` requires $\lceil L_{\text{trgm}} \times 0.35 \rceil = 2$ shared trigrams, matching **`5,000–23,400` whale rows** on common Vietnamese syllable onsets (such as `"ch"`, `"gi"`, `"kh"`, `"d"` — directly observed in FU-SL-1 `medium/item/fuzzy/q1` `"cháy"`, which scanned `8,989` rows on a `50k` medium tenant in `50.44 ms` and caused all `7/20` timeouts in `connect_probe` `medium_fuzzy`).
  - Because `SPEC §6.2 / §6.4` strictly orders `tier DESC` (`Tier 3 exact prefix > Tier 2 folded prefix > Tier 1 fuzzy`), for **`819 / 1,000` (`81.9%`)** of C1-L queries (including **100% of the 2-, 3-, and 4-rune `prefix` and `folded` queries**), Tier 3 + Tier 2 already produce $\ge 7$ rows (`fetchLimit = 7`). Thus the `40–125 ms` GIN trigram scan and heap recheck for Tier 1 was **100% discarded by `LIMIT 7`**.
- **Changes shipped (`a303b85`, `d282409`, `4d682ad`, `c2ff223`, `advisor-dec-353`):**
  - Rewrote all four lexical queries (`SearchItemsLexical`, `SearchTagsLexical`, `SearchItemsLexicalPage`, `SearchTagsLexicalPage` in `apps/api/internal/db/queries/search_lexical.sql` + `sqlc v1.30.0` regeneration in `apps/api/internal/db/gen/search_lexical.sql.go`) as a single-statement tiered `UNION ALL`:
    1. `prefix_ranked`: selects Tier 3 + Tier 2 rows with an inlined `IMMUTABLE` folded-prefix expression (`replace(replace(replace(immutable_unaccent(qn), '\', '\\'), '%', '\%'), '_', '\_') || '%'`), allowing PostgreSQL to constant-fold the pattern under `force_custom_plan` and use `BitmapOr` over the B-tree prefix indexes (`*_name_prefix`, `*_unaccent_prefix`) with **zero GIN scan**, ordered by `tier DESC, score DESC, last_used_at DESC, count DESC, id ASC LIMIT page_limit`.

Commit `4d682ad` restored the exact original `round(GREATEST(similarity(...), word_similarity(...))::numeric, 2)::float8` expression in all 8 query arms, and commit `c2ff223` added explicit `ß`/`sss`/`ssh` and `©` DB regressions to `TestLexicalOldVsNewEquality` (`> 4,300` exact old-vs-new SQL comparisons across unpaged and keyset-paged queries, `0` mismatches).
