## 2. Contract chuẩn cho mọi task

### 2.1 Cookie, CSRF và thời hạn

Tất cả cookie là host-only (không `Domain`), `Secure`, `SameSite=Lax`; chỉ CSRF và preference được JS đọc. Production bắt buộc HTTPS. Local dùng đúng `http://localhost:3000` theo P01; kiểm hành vi Secure cookie trên browser mục tiêu, dùng HTTPS local nếu browser không hỗ trợ ngoại lệ localhost, không tắt Secure cho production.

| Cookie | Giá trị | Path | Thời hạn | HttpOnly |
|---|---|---|---|---|
| `sabk_session` | Access JWT HS256 | `/api` | 10 phút, không vượt hạn session | Có |
| `sabk_refresh` | Opaque CSPRNG 32 byte, base64url | `/api/v1/auth` | Tối đa 30 ngày từ lúc cấp session | Có |
| `sabk_csrf` | Nonce và chữ ký gắn subject | `/` | Theo session; anonymous 10 phút | Không |
| `sabk_anon` | Opaque browser nonce cho pre-auth | `/api/v1/auth` | 10 phút | Có |
| `sabk_oauth` | Browser binding opaque, server giữ transaction | `/api/v1/auth` | 10 phút | Có |
| `sabk_reauth` | Receipt opaque, server giữ hash và action | `/api/v1/auth` | 2 phút, không vượt deadline flow | Có |
| `sabk_locale`, `sabk_theme` | Cache preference đã validate | `/` | 1 năm | Không |

Session có **hạn tuyệt đối 30 ngày**, refresh không kéo dài vô hạn. Hạn access là `min(now + 10m, session.expires_at)`. Xoá cookie đúng path/flags; không xoá preference khi logout. Đây là policy P02 bổ sung vì SPEC chưa chốt hạn refresh.

`GET /auth/csrf` trả 204 và chuẩn bị cookie. Nếu session còn hiệu lực, ký CSRF theo session ID; nếu access hết hạn, có thể nhận diện session bằng refresh hash hiện tại hoặc lịch sử, nhưng chưa rotate/revoke tại bootstrap. Chưa có session thì dùng nonce anonymous HttpOnly và token HMAC gắn nonce đó. Không reset nonce hợp lệ sau mỗi GET; bootstrap không là một cách đăng nhập. Dùng prefix khác nhau cho chữ ký anonymous và session, so chữ ký constant-time.

Mọi unsafe request kiểm đúng `Origin == APP_ORIGIN`, content type JSON và `X-CSRF-Token` bằng cookie có chữ ký. Bootstrap/login/signup/verification dùng subject phù hợp; signed-out verification vẫn phải đăng nhập đúng user trước khi confirm. Thiếu hoặc sai Origin/CSRF bị reject, không dựa riêng SameSite. `GET /auth/csrf` từ cross-site bị reject qua Fetch Metadata khi có; không bật credentialed CORS cho origin khác.

OAuth callback là ngoại lệ browser redirect không mang header CSRF: thay bằng state + cookie binding + transaction dùng một lần. GET OAuth start chỉ cho login; link và re-auth dùng POST có CSRF. Không dùng query `mode=link` để bỏ qua middleware.

### 2.2 Session và refresh

JWT chỉ chứa claim version, issuer, audience, `sub=user_id`, `sid=session_id`, `iat`, `exp`, `jti`; allowlist HS256, kiểm đủ issuer/audience/expiry. Secret JWT khác secret CSRF và re-auth. Mỗi request private kiểm session DB còn hiệu lực và user chưa bị xoá; JWT còn hạn không được vượt revoke.

`POST /auth/refresh` không đi qua middleware yêu cầu access token còn hạn:

1. Hash refresh opaque, mở transaction; tìm và lock session theo hash hiện tại hoặc hash lịch sử.
2. Kiểm user/session chưa xoá/revoke/hết hạn, Origin và CSRF gắn **session tìm được**. CSRF sai không gây revoke session của nạn nhân.
3. Hash hiện tại: tạo secret mới, chuyển hash cũ vào `session_refresh_used`, cập nhật hash mới, giữ hạn tuyệt đối và commit.
4. Hash đã dùng, sau khi xác thực CSRF: commit revoke cả session và audit reuse, rồi trả `401 session_invalid`. Hash lạ chỉ reject.
5. Response thành công đặt cookie access/refresh mới. CSRF session giữ ổn định để tab khác không bị lỗi header cũ.

Policy giữ rotation nghiêm ngặt, **không grace window**. Test hai request cùng token phải có một rotation; nhánh reuse commit revoke khiến cả access vừa cấp cũng không dùng tiếp được. Giữ lịch sử hash ít nhất đến hết hạn tuyệt đối session, không prune sớm theo một TTL ngắn hơn.

Client điều phối refresh trong tab và giữa các tab (Task 19). Response refresh bị mất sau commit vẫn có thể buộc đăng nhập lại; không retry refresh mù. Đây là giới hạn được ghi ADR và UI, không coi là lỗi password. Logout cũng có đường xác minh bằng refresh + CSRF khi access đã hết; request hợp lệ với session đã revoke có thể clear cookie và trả 204.

### 2.3 DTO, lỗi và phân trang

`Me` trả cùng shape cho signup (201), login (200), `GET /auth/me` (200), cập nhật settings/password (200):

```ts
type Me = {
  user: { id: string; email: string; email_verified: boolean; created_at: string };
  settings: {
    locale: 'en' | 'vi';
    theme: 'system' | 'light' | 'dark';
    auto_lock_minutes: 0 | 5 | 15 | 60;
    semantic_suggest: boolean;
  };
  identities: Array<{ provider: 'password' | 'google' | 'github'; linked_at: string }>;
  features: {
    semantic_available: boolean;
    email_verification_required: boolean;
    oauth_providers: Array<'google' | 'github'>;
    oauth_reauth_providers: Array<'google'>;
    password_enrollment_available: boolean;
    captcha_site_key: string | null;
  };
  vault: { status: 'absent' | 'present' };
};
```

Đây là shape để đưa vào OpenAPI; TS dùng type **sinh từ schema** khi triển khai. Server chỉ biết vault tồn tại; `locked`/`unlocked` là trạng thái crypto client của P03. P02 `VaultStatusProvider` trả `absent`, P03 thay bằng query thật. Trước login, `GET /auth/config` trả provider đang bật, yêu cầu verification và public CAPTCHA site key; không lộ secret hay capabilities gắn một user cụ thể.

Tên API chuẩn là `semantic_suggest`, lưu ở JSONB `app_user.settings`; locale/theme/auto-lock là cột theo SPEC. PATCH không gửi field thì giữ nguyên, `null`/unknown field bị 400. Bật semantic khi probe runtime báo unavailable trả `409 semantic_unavailable` và không lưu bất kỳ field nào của patch đó. Preference true có thể tồn tại khi provider down; availability và preference là hai thông tin khác nhau. Không đổi preference thành false chỉ vì tạm mất TEI.

Lỗi dùng RFC 9457 và code snake_case của P01. Code mới phải có ở Go problem catalog, TS catalog và OpenAPI trong cùng thay đổi. `401 access_expired` chỉ dành cho JWT hết hạn trên route protected; thiếu JWT dùng `unauthenticated`, revoked/refresh invalid dùng `session_invalid`, login sai dùng `invalid_credentials`. Web không refresh mọi loại 401. Các nhóm còn lại: `csrf_invalid`, `forbidden`, `invalid_request`, `reauth_required`, `reauth_invalid`, `reauth_unsupported_provider`, `rate_limited`, `captcha_required`, `email_not_verified`, `email_taken`, `identity_conflict`, `identity_last_method`, `oauth_state_invalid`, `oauth_provider_error`, `verification_invalid`, `password_weak`, `semantic_unavailable`, `mail_delivery_unavailable` (503).

`429` có header `Retry-After` (giây nguyên dương); body có `retry_after` cùng giá trị. CAPTCHA có `captcha_required` trong extension của problem khi cần, không kèm email. Login sai/không tồn tại/OAuth-only có cùng lỗi và cùng đường hash giả. Lockout 429 và CAPTCHA phải xuất hiện cả với email không tồn tại. Signup/email collision 409 là disclosure có chủ ý trong mockup, ghi riêng ADR.

`session_invalid` có extension `reason: revoked | expired | invalid`; chỉ trả revoked/expired khi token đã xác minh cho phép nhận diện session, token lạ dùng invalid. P03 cần `reason=revoked` để xoá remembered-device wrap theo SPEC §5.6. Logout hoặc expiry bình thường không tự xoá DevKey; mọi trường hợp mất auth đều xoá plaintext/VK memory khi P03 tích hợp.

Mọi list dùng `{items, next_cursor}` và `limit` 1..100 (mặc định 50), cursor keyset có cả timestamp lẫn ID. ID audit/notification là `bigserial` trong DB, **decimal string** trong JSON để không mất precision; session/identity ID là UUID. Cursor validate, scope query luôn lấy user từ principal, không nhận user_id từ client.

### 2.4 Re-auth và tài khoản OAuth-only

Grant HMAC có version, user ID, session ID, **một action**, issued-at, expiry và nonce; TTL cố định 5 phút. So chữ ký constant-time, `now >= exp` là hết hạn; reject thời gian tương lai/TTL dài hơn policy. Header mutation là `X-Reauth-Token`. Grant chỉ ở memory client, không URL, cookie, persisted query cache hoặc telemetry.

| Action | Nơi tiêu thụ |
|---|---|
| `account.email_change` | Yêu cầu đổi email |
| `account.password_change` | Đổi password đã có hoặc tạo password bằng re-auth hợp lệ |
| `account.identity_link` | Bắt đầu liên kết provider |
| `account.identity_unlink` | Gỡ identity, không gỡ phương thức cuối |
| `session.revoke_others` | Thu hồi các session khác |
| `vault.rewrap` | P03 `PUT /vault/kek` |
| `vault.recover` | P03 recovery complete |
| `vault.recovery_keys_regenerate` | P03 bù RK |
| `vault.recovery_keys_rotate` | P03 thay đủ RK |
| `vault.passkey_register` | P03 lưu credential và wrap |
| `vault.passkey_revoke` | P03 thu hồi passkey |
| `vault.reset` | P03/P04 reset vault |
| `export.decrypted` | P06 ghi audit trước decrypted export |
| `account.delete` | P06 xoá tài khoản |

Registry có các action downstream nhưng không mount endpoint P03/P06 ở P02. Grant không được consume riêng lẻ; có thể dùng lại cho đúng action trong TTL nếu session còn sống. P03 giữ idempotency theo SPEC. Revoke session vô hiệu mọi grant. Đổi password sẽ thay session hiện tại và revoke các session cũ, nên grant trước đổi cũng hết tác dụng.

| Phương thức | Bằng chứng | Policy |
|---|---|---|
| Password | Verify password đăng nhập của user hiện tại, có rate limit | Cấp grant cho action đã validate |
| Google | ID token kiểm issuer/audience/expiry/nonce/sub; flow mới có `auth_time` chứng minh freshness | Chỉ bật re-auth khi adapter kiểm chứng capability. Không mặc định Google hỗ trợ `prompt=login`, `max_age` hoặc luôn trả `auth_time` |
| GitHub | OAuth code + verified primary email từ `/user/emails`, subject `/user.id` | Dùng login/link. Callback im lặng không chứng minh fresh authentication; không cấp re-auth grant |

Freshness Google: `auth_time >= flow.started_at - 120s`, `auth_time <= now + 30s`, callback trong hạn flow; missing/stale claim phải fail closed. Fake provider kiểm cả ca có/thiếu claim; P06 xác minh cấu hình thật trước khi bật capability production. Một provider được bật login không đồng nghĩa được bật re-auth.

**Đặt password đầu tiên cho OAuth-only:** Khi provider không hỗ trợ freshness, dùng enrollment qua email **đang verified của chính tài khoản**, độc lập với `AUTH_REQUIRE_EMAIL_VERIFICATION`:

- `POST /auth/password/enroll/send`, session + CSRF; chỉ khi chưa có password và email hiện tại đã verified. Token CSPRNG 32 byte, hash-only, purpose `password_enroll`, gắn user/session/email hiện tại, TTL 10 phút.
- Người dùng mở link ở cùng session và nhập password mới. `POST /me/password` nhận `{new_password, enrollment_token}`; lock user/identity/token, kiểm vẫn chưa có password, email/session chưa đổi, consume token và tạo hash trong cùng transaction.
- Nếu có fresh re-auth hỗ trợ, có thể dùng grant `account.password_change` thay token để tạo password. Hai loại proof loại trừ nhau; password đã tồn tại **luôn** cần grant, không nhận enrollment token.
- Sau commit, cấp session mới/CSRF mới và revoke các session cũ. Email proof chỉ cho quyền thêm password lần đầu, không cấp grant vault, không mở VK và không xác minh email chưa verified thay cho signup flow.
- Token lỗi/hết hạn/replay/sai session trả lỗi chung; resend vô hiệu token cũ cùng purpose. Bổ sung này phải được ghi rõ SPEC §3.1/§7.6/§9 và ADR ở Task 1; không diễn giải thành email recovery vault hoặc password reset.

### 2.5 OAuth, verification và transaction

OAuth lưu server-side transaction gồm provider, mode, state hash, cookie binding hash, PKCE verifier, nonce, expected user/session (link/reauth), action, started_at, expires_at và consumed_at. Verifier ngắn hạn chỉ dùng đổi code; không log, xoá khi dùng/hết hạn. Callback claim transaction atomic để chỉ một request exchange; provider fail yêu cầu khởi động flow mới. Kiểm state/provider/cookie/session cả nhánh lỗi/cancel trước khi cập nhật trạng thái.

Login callback chỉ lưu kết quả identity đã xác minh trong transaction OAuth ở trạng thái `ready`; chưa phát cookie session. Web gọi `POST /auth/oauth/complete` với cookie binding + CSRF trong cùng Web Lock với refresh/logout. Endpoint lock transaction ready, kiểm hạn/binding, tạo hoặc tìm user/identity + cấp session + consume completion atomic, rồi mới set cookie. Completion tối đa 2 phút sau callback và không vượt hạn flow 10 phút. Cách này tránh response refresh cũ ghi đè session vừa đăng nhập bằng OAuth. Xoá cookie OAuth sau complete/cancel, không xoá trước khi browser dùng completion.

Login tìm `(provider, provider_uid)`; email trùng không tự link. Provider đã liên kết không được chuyển sang user khác theo email mới trả về. Link cần session + grant ở start, lưu deadline grant vào flow và kiểm user/session/deadline lại khi callback; new provider không được dùng để chứng minh quyền link chính nó. Unique constraint và user lock chống hai callback link/unlink cạnh tranh làm mất phương thức đăng nhập cuối.

OAuth re-auth callback không trả grant qua URL: tạo receipt server-side gắn user/session/provider/action, cookie chỉ là token opaque. `POST /auth/reauth` consume receipt cùng action đúng một lần để đổi grant. URL callback web chỉ có provider trong path và status allowlist: `login_ready`, `linked`, `reauth_ready`, `cancelled`, `identity_conflict`, `invalid_flow`, `provider_error`, `reauth_unavailable`. Email collision tại login complete là API problem `email_taken`. Dùng redirect đích cố định, không nhận return URL tuỳ ý.

Verification email có token hash-only TTL 24 giờ cho signup, 30 phút cho đổi email. Send/supersede và confirm dùng transaction; confirm lock token + user, kiểm target/expected email vẫn đúng, expire/reuse và uniqueness. Consume token, đổi email/verified_at, huỷ các proof email/enrollment cũ của user, audit và tạo in-app notice cùng transaction; đổi email đi rồi đổi về không làm proof cũ sống lại. Revoke session khởi tạo change-email thì pending change cũng không dùng được.

Link email dùng fragment `#token=...`; web lấy vào memory và `history.replaceState` xoá ngay, không analytics trên trang đó. GET trang không consume token; nút xác nhận POST cần đúng session + CSRF. Mở ở thiết bị chưa đăng nhập thì yêu cầu đăng nhập rồi mở lại link; không đưa token vào `returnTo` hoặc persisted storage. Trang có `Referrer-Policy: no-referrer` và no-store.

## 3. Endpoint và operationId

Tất cả path dưới đây tương đối với `/api/v1`. `S` là session DB còn hiệu lực; `C` là Origin + CSRF; `A` là action re-auth. Response lỗi dùng catalog mục 2.3. OpenAPI ghi rõ security cho từng operation, không gán bearer scheme thay cookie.

| Method / path | operationId | Điều kiện / response |
|---|---|---|
| `GET /auth/config` | `authConfig` | Public; public providers/verification/CAPTCHA, no-store |
| `GET /auth/csrf` | `authCsrf` | Bootstrap theo mục 2.1; 204 + cookie |
| `POST /auth/signup` | `authSignup` | C anonymous hoặc session; `{email,password,locale?}`; 201 Me + cookie |
| `POST /auth/login` | `authLogin` | C; `{email,password,captcha_token?}`; 200 Me + cookie |
| `POST /auth/refresh` | `authRefresh` | Refresh + C, không cần access còn hạn; 204 + cookie |
| `POST /auth/logout` | `authLogout` | Session/refresh + C; 204 clear cookie |
| `GET /auth/me` | `authMe` | S; 200 Me |
| `GET /auth/oauth/{provider}/start` | `authOauthStart` | Login-only; 302 đến provider |
| `POST /auth/oauth/{provider}/link` | `authOauthLinkStart` | S+C+A `account.identity_link`; 200 `{authorization_url}` |
| `POST /auth/oauth/{provider}/reauth` | `authOauthReauthStart` | S+C; `{action}`; 200 `{authorization_url}`, provider hỗ trợ freshness |
| `GET /auth/oauth/{provider}/callback` | `authOauthCallback` | State/cookie/transaction; 303 về web với status allowlist |
| `POST /auth/oauth/complete` | `authOauthComplete` | C + browser binding + login transaction ready; 200 Me + cookie, consume một lần |
| `POST /auth/reauth` | `authReauth` | S+C; `{action,password}` hoặc `{action,provider}` + receipt; 200 `{grant,action,expires_at}` |

## 6. Bàn giao cho P03 và rollout

**P03 nhận:** `authctx.Principal`; session/CSRF/reauth middleware; registry action và kiểm grant trong transaction; `Me.vault.status` existence provider; hook client session epoch; audit/notification có transaction và mail adapter; account settings/verification state; test harness user A/B và fake clock.

P03 thay provider vault absent bằng query bảng vault, giữ tồn tại kho riêng với local lock state. `POST /vault` kiểm email flag + verified ở server; recovery không thêm điều kiện email mới. P03 dùng các action rewrap/recover/RK/passkey/reset đúng bảng mục 2.4 và giữ idempotency/If-Match theo SPEC. Hook session nhận `reason=revoked` để xoá DevKey/wrap thiết bị theo §5.6, trong khi logout chỉ xoá bí mật trong memory. Không dùng client `unlocked` làm proof tài khoản.

**Các bước rollout khi triển khai:**

1. Kiểm P01 gate và backup DB hiện có; chạy migration forward bổ sung bảng, không drop dữ liệu P01.
2. Đưa API/worker có config hợp lệ lên trước UI cần contract mới; smoke profile local/fake trước. Public OAuth disabled nếu chưa có cấu hình, không nút hỏng.
3. Qua gate backend, UI và E2E matrix; lưu evidence/known limitations rồi mới đánh dấu P02 hoàn tất và bàn giao P03.
4. Nếu policy/token lỗi, dừng phát session mới, revoke session/receipt/transaction ảnh hưởng và yêu cầu login lại. Rollback binary tương thích schema; không dùng migration down/drop account/vault như recovery mặc định.
5. Nếu thay key signing, ghi rõ session/grant nào bị vô hiệu; test restart/rollback cookie policy. Không phục hồi DB cũ để lấy lại session đã revoke.

**Còn thuộc P06:** Smoke Google/GitHub với credentials/callback thật; xác minh Google freshness trước bật re-auth capability; mail delivery production; trusted proxy topology production; Turnstile thật/CSP, backup/restore và kiểm tra phát hành. Fake-provider tests không thay các mục này. Nếu deployment không dùng được freshness, OAuth login vẫn dùng được và người dùng dùng enrollment/password cho thao tác nhạy cảm.
