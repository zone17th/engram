## 2. Contract chuẩn cho mọi task

### 2.1 Byte layout và encoding

ADR 0002 (Task 1) chốt layout dưới đây; code và vectors theo ADR, không theo plan nếu hai bên lệch.

| Blob | Layout (bytes) | AAD |
|---|---|---|
| Wrap chung (KEK, RK, PRF, priv) | `version(1)=0x01` ‖ `nonce(24)` ‖ `ciphertext+tag(32+16)` cho VK; private-key blob dài hơn | Chuỗi ASCII theo loại, không NUL: `vault-key-v1`, `vault-key-rk-v1`, `vault-key-passkey-v1`, `priv-keys-v1` |
| Private keys | Plaintext = `x25519_seed(32)` ‖ `ed25519_seed(32)`, wrap bằng VK | `priv-keys-v1` |
| Entry | Envelope JSON + `ciphertext` bytea riêng, không prefix | §5.5: `sabk.entry.v1` ‖ `0x00` ‖ JCS(envelope) ‖ `0x00` ‖ entry_id |
| DevKey wrap (chỉ IndexedDB) | WebCrypto AES-GCM 256, `iv(12)` ‖ `ciphertext+tag` | `sabk.devkey.v1` ‖ `0x00` ‖ user_id ‖ `0x00` ‖ vault_key_id |

- AEAD là `crypto_aead_xchacha20poly1305_ietf`; nonce 24 B ngẫu nhiên mỗi lần seal. Byte `version` đứng đầu để sau này đổi layout không phải đoán.
- JSON truyền bytes bằng **base64url không padding**; Go decode strict, từ chối padding, ký tự lạ và độ dài sai. Cột DB là `bytea`.
- KDF params trên `vault.kdf` đúng 5 field `{"alg":"argon2id13","ops":3,"mem":67108864,"parallelism":1,"salt":"<b64url 16B>"}`. Server từ chối field thiếu/thừa, `ops<3`, `mem<67108864`, `parallelism≠1` hoặc salt sai độ dài. Client không bao giờ derive với params thấp hơn, kể cả khi server trả params thấp hơn (fail closed).
- `vault_key_id` do server sinh: `vk:` + 16 B ngẫu nhiên base64url. Duy nhất toàn cục, đổi khi reset, không đổi khi rewrap/recover.

### 2.2 Recovery key

- Sinh: 16 B CSPRNG → Crockford Base32 26 ký tự (130 bit, 2 bit cao của ký tự đầu luôn 0) → hiển thị `rk{n}_XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX`, `n` = 1…10 theo vị trí lúc sinh.
- **Chuẩn hoá đúng một hàm dùng chung** cho sinh, lookup và wrap: trim, bỏ khoảng trắng và `-`, prefix về chữ thường `rk{n}_`, phần Crockford về chữ hoa, alias `O→0`, `I/L→1`, bỏ `U`; từ chối ký tự ngoài bảng, độ dài khác 26, `n` ngoài 1…10 hoặc 2 bit cao khác 0. Chuỗi đã chuẩn hoá là `rk{n}_` + 26 ký tự, không hyphen.
- `lookup_hash = BLAKE2b-256(UTF8("sabk.rk.lookup.v1") ‖ UTF8(rk_norm))`; `wrap_key = BLAKE2b-256(UTF8("sabk.rk.wrap.v1") ‖ UTF8(rk_norm))`. Không dùng 16 B raw làm key AEAD.
- Plaintext RK chỉ tồn tại trong Worker và trong DOM của lưới hiển thị; xoá khỏi state khi rời bước, không ghi vào history, query cache, IndexedDB, log hay evidence.

### 2.3 Concurrency, idempotency và thứ tự middleware

- `GET /vault` trả header `ETag: "<version>"`. Mọi mutation vault (trừ `POST /vault` và `POST /vault/unlock/*`) bắt buộc `If-Match: "<version>"`: thiếu → `428 precondition_required`; lệch → `412 version_mismatch` kèm `current_version` trong extension. Server lock hàng `vault` (`SELECT … FOR UPDATE`) rồi mới so version.
- `Idempotency-Key` bắt buộc cho `POST /vault`, `POST /vault/passkeys`, `POST /vault/recover/complete`, `POST /vault/recovery-keys/regenerate`, `POST /vault/recovery-keys/rotate`: chuỗi 16–128 ký tự `[A-Za-z0-9_-]`, client sinh UUID v4 mỗi lần thao tác của người dùng (không mỗi lần retry).
- Fingerprint = SHA-256 của `method ‖ 0x00 ‖ route pattern ‖ 0x00 ‖ body bytes đã nhận`. Bảng `idempotency_key` thêm cột `status` (`in_progress` | `done`), `status_code`, `expires_at` so với SPEC §8 (Task 1 cập nhật SPEC).
- Luồng middleware cho route có idempotency, đúng thứ tự:
  1. `RequireOrigin` → `RequireSession` → `RequireCSRF` → `RequireJSONContent`.
  2. **Idempotency lookup** theo `(user_id, key)`: `done` + cùng fingerprint → trả response đã lưu (status + body) và dừng, **không** kiểm grant; `done`/`in_progress` + fingerprint khác → `409 idempotency_conflict`; `in_progress` + cùng fingerprint → `409 idempotency_in_progress` kèm `Retry-After: 1`.
  3. `RequireReauth(action)` và `If-Match` cho lần chạy đầu.
  4. Handler chạy mutation; insert bản ghi `done` + response **trong cùng transaction** với mutation. Lỗi 4xx/5xx không ghi bản ghi, nên retry được đánh giá lại từ đầu.
- Đúng như SPEC: retry của mutation đã commit cần session + CSRF hợp lệ nhưng không cần grant còn sống; mutation không bao giờ chạy hai lần. Bản ghi hết hạn sau 24 giờ; job worker xoá hàng `expires_at < now()` theo lô, idempotent.
- Hai request cùng key chạy song song: request đầu insert `in_progress` bằng `INSERT … ON CONFLICT DO NOTHING` trong transaction riêng ngắn rồi mới vào mutation; request sau thấy `in_progress`. Nếu request đầu chết giữa chừng, hàng `in_progress` quá 60 giây được coi là bỏ dở và cho phép chạy lại.

### 2.4 Rate limit

| Scope | Giới hạn | Khoá đếm | Ghi chú |
|---|---|---|---|
| `POST /vault/unlock/recovery` | 5 / 15 phút | user_id | Đếm **mọi** request, kể cả trúng, để số lần trúng/trượt không thành oracle |
| `POST /vault/recover/complete` | 5 / 15 phút | user_id | Dùng chung bucket với unlock recovery |
| `POST /vault/unlock/passkey/options`, `POST /vault/passkeys/register/options` | 20 / phút | user_id | |
| `PUT /vault/kek`, regenerate, rotate, `DELETE /vault`, `POST/DELETE /vault/passkeys*` | 10 / phút | user_id | Write limit chung §9.1 |

- Counter lưu Postgres (bảng `rate_counter`, fixed window theo `scope` + subject hash), không in-memory, để nhiều instance và đổi IP/thiết bị không né được. Vượt hạn trả `429 rate_limited` + `Retry-After`; body không nói còn bao nhiêu RK hay passphrase đúng một phần.
- **Passphrase unlock không có rate limit server thực sự**: client tải `wrapK` qua `GET /vault` rồi thử offline; server không biết passphrase đúng hay sai. ADR 0002 ghi rõ đây là giới hạn của mô hình, bảo vệ dựa vào Argon2id 64 MiB + zxcvbn ≥ 3. P03-B8 vì vậy áp cho recovery và passkey options; `GET /vault` chỉ chịu read limit chung, không 5/15 phút (nếu không app tự khoá người dùng khi reload).

### 2.5 WebAuthn

- RP ID và origin lấy từ config: production `key.zone17th.click` / `https://key.zone17th.click`; dev `localhost` / đúng `APP_ORIGIN` kể cả port. Server dùng thư viện verify registration đã pin (đề xuất `github.com/go-webauthn/webauthn`), không tự parse CBOR.
- Bảng `webauthn_challenge`: `id`, `user_id`, `session_id`, `purpose` (`register` | `unlock`), `challenge_hash`, `prf_salt` (với `register`), `expires_at` (5 phút), `consumed_at`. Challenge 32 B ngẫu nhiên, chỉ lưu hash, dùng một lần, gắn session hiện tại.
- **Đăng ký** (re-auth `vault.passkey_register` lấy trước khi mở dialog):
  1. `POST /vault/passkeys/register/options` → creation options + server sinh `prf_salt` 32 B, lưu cùng challenge.
  2. Client `create()`. PRF `enabled !== true` → `passkey.prf_unsupported`, dừng. Có `results.first` thì dùng luôn; chỉ `enabled=true` thì gọi `get()` với credential vừa tạo, `userVerification: required`, `prf.eval.first = prf_salt` và **challenge ngẫu nhiên do client sinh**: assertion này không gửi server và không chứng minh gì với server, chỉ để lấy PRF output. ADR 0002 ghi lý do.
  3. Worker seal VK bằng PWK, mở thử lại đúng VK, rồi `POST /vault/passkeys` với `{challenge_id, attestation: {client_data_json, attestation_object}, prf_salt, vk_wrap, name}`.
  4. Server consume challenge (đúng user/session/purpose, chưa hết hạn, chưa dùng), verify clientData type/challenge/origin, rpIdHash, flags UP+UV, attestation `none` chấp nhận, và **tự trích** `cred_id`, `pubkey`, `aaguid` từ attestation. Không nhận các field này do client khai. `prf_salt` phải khớp salt đã lưu cùng challenge.
- **Unlock**: `POST /vault/unlock/passkey/options` trả `allowCredentials`, `prf.evalByCredential` (mỗi credential một salt), `vk_wrap` theo credential, challenge server sinh (purpose `unlock`). Assertion **không** gửi lại server ở P03: unlock là thao tác cục bộ, không tạo session. Không dùng một salt cho nhiều credential.
- Không có PRF thì không đăng ký; không fallback largeBlob hay secret do server giữ.

### 2.6 Trạng thái client và vòng đời VK

- State machine trong `features/vault`: `no_vault` → `onboarding` → `unlocked`; `locked` ↔ `unlocking` → `unlocked`; `recovering`, `rewrapping`, `resetting`, `error`. Server chỉ biết `absent`/`present` (`Me.vault.status`); `locked`/`unlocked` là trạng thái crypto của client và **không** là proof cho server.
- Mỗi lần lock/logout/đổi user tăng `generation` trong Worker. Kết quả của lệnh gửi trước đó mang generation cũ bị huỷ, không đưa plaintext trở lại UI.
- Lock xoá VK/KEK/PWK trong Worker (`sodium_memzero` trên mọi buffer giữ key), xoá query cache của body đã giải mã, reset form chứa secret. JS không đảm bảo xoá mọi bản copy string khỏi heap; giảm lifetime và reference, không hứa memory zero tuyệt đối (ghi ADR).
- Auto-lock theo `settings.auto_lock_minutes` (0 = never, mặc định 15), đếm idle theo tương tác người dùng trong tab; nhiều tab đồng bộ lock qua `BroadcastChannel` có sẵn ở `lib/auth/broadcast.ts`. Phím `L`, nút khoá và "Lock now" khoá ngay.
- Logout: xoá VK/plaintext, **giữ** DevKey; lần đăng nhập sau phải xác thực tài khoản trước khi silent unlock. `401 session_invalid` với `reason=revoked` → xoá IndexedDB của user đó. Đổi user trong cùng browser không bao giờ dùng DevKey của user khác (namespace theo `user_id` + `vault_key_id`).

## 3. Endpoint và operationId

Path tương đối với `/api/v1`. `S` session, `C` Origin + CSRF, `A` grant re-auth (action trong ngoặc), `M` `If-Match`, `I` `Idempotency-Key`. Bảng này là contract cho OpenAPI; Task 1 sửa §9.2 cho khớp.

| Method / path | operationId | Điều kiện / response |
|---|---|---|
| `GET /vault` | `vaultGet` | S; 200 `{vault_key_id, version, kdf, vault_key_wrapped_by_kek, x25519_public, ed25519_public, private_keys_wrapped, recovery_keys_remaining, passkeys:[{id,name,aaguid,created_at}]}` + ETag; 404 `vault_absent` |
| `POST /vault` | `vaultCreate` | S+C+I; body đủ trường §8 + `recovery_keys` đúng 10; 201 `{vault_key_id, version}`; 409 `vault_exists`; 403 `email_not_verified` khi cờ bật |
| `PUT /vault/kek` | `vaultRewrap` | S+C+A(`vault.rewrap`)+M; `{kdf, vault_key_wrapped_by_kek}`; 200 `{version}`; audit + notice + mail |
| `DELETE /vault` | `vaultReset` | S+C+A(`vault.reset`)+M; 204; gọi reset hook (P04 xoá entry) |
| `GET /vault/recovery-keys` | `vaultRecoveryKeysGet` | S; 200 `{remaining, slots:10}` |
| `POST /vault/unlock/recovery` | `vaultRecoveryLookup` | S+C, rate limit; `{lookup_hash}`; 200 `{recovery_key_id, wrap}`; 401 `recovery_key_invalid`; không consume |
| `POST /vault/recover/complete` | `vaultRecoverComplete` | S+C+A(`vault.recover`)+M+I, rate limit; `{recovery_key_id, kdf, vault_key_wrapped_by_kek}`; 200 `{version}` |
| `POST /vault/recovery-keys/regenerate` | `vaultRecoveryKeysRegenerate` | S+C+A(`vault.recovery_keys_regenerate`)+M+I; `{recovery_keys:[…]}` 1…(10−remaining); 200 `{remaining, version}` |
| `POST /vault/recovery-keys/rotate` | `vaultRecoveryKeysRotate` | S+C+A(`vault.recovery_keys_rotate`)+M+I; đúng 10; 200 `{remaining:10, version}` |
| `POST /vault/passkeys/register/options` | `vaultPasskeyRegisterOptions` | S+C, rate limit, vault present; 200 `{challenge_id, public_key: CreationOptions, prf_salt}` |
| `POST /vault/passkeys` | `vaultPasskeyCreate` | S+C+A(`vault.passkey_register`)+I; mục 2.5; 201 `{id, name, aaguid, created_at}` |
| `GET /vault/passkeys` | `vaultPasskeysList` | S; 200 `{items}` metadata, không wrap |
| `PATCH /vault/passkeys/{id}` | `vaultPasskeyRename` | S+C, owner; `{name}`; 200; chỉ khi UI giữ rename (mockup `settings.html` có nút đổi tên) |
| `DELETE /vault/passkeys/{id}` | `vaultPasskeyRevoke` | S+C+A(`vault.passkey_revoke`), owner; 204 |
| `POST /vault/unlock/passkey/options` | `vaultPasskeyUnlockOptions` | S+C, rate limit; 200 `{challenge_id, public_key: RequestOptions, credentials:[{id, prf_salt, vk_wrap}]}` |

`PUT /vault/kek` không đổi passkey, RK hay `vault_key_id`. Passkey register/revoke không tăng `vault.version` (không ảnh hưởng wrap khác); rewrap, recover, regenerate, rotate tăng version. Ghi quy ước này vào SPEC §8.

## 7. Bàn giao cho P04 và rollout

**P04 nhận:** crypto client (`sealEntry`/`openEntry` với AAD theo entry_id), envelope validator TS và Go, vectors, idempotency + If-Match middleware dùng lại cho `POST /items`, `POST /tags`, entries; `vault_key_id` từ `GET /vault` cho envelope; `ResetHook` để xoá entry; locked state U5 để gắn body thật; rate limit write.

**Rollout khi triển khai:**

1. Backup DB, chạy `0005_vault` forward; không đụng bảng P02.
2. Đưa API lên trước UI; khi UI chưa bật, `Me.vault.status` vẫn đúng và không có nút hỏng.
3. Qua gate mục 6 + CI + evidence rồi mới đánh dấu P03 xong và mở P04.
4. Khi phát hiện lỗi wrap/regression crypto: dừng mutation tạo key mới (`POST /vault`, rewrap, rotate, passkey register), giữ nguyên ciphertext và wrap để điều tra; **không** tự reset vault người dùng, không hạ KDF, không nâng envelope version làm workaround.
5. Rollback binary phải tương thích schema `0005`; không dùng migration down trên production.

**Còn thuộc P06:** smoke PRF đa authenticator trước beta nếu P03 chưa có thiết bị thật, CSP/SRI cho bundle chứa Worker, kiểm backup/restore với semantics §5.9 và §10.5.
