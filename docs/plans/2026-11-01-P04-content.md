### 2.1 Mô hình dữ liệu (migration `0006_content`)

Theo §8, với các điểm bổ sung đánh dấu ★ (Task 1 cập nhật §8):

| Bảng | Cột chính | Ràng buộc/ghi chú |
|---|---|---|
| `item` | `id uuid PK` (client có thể gửi, mục 2.7), `user_id`, `name` 1–200, `name_normalized` 1–200, `name_unaccent` generated, `hint` ≤120, `entry_count int`, ★`version int NOT NULL DEFAULT 1`, `last_used_at`, `created_at`, `updated_at`, `deleted_at`, ★`delete_batch uuid` | `UNIQUE (user_id, id)`; index §8 (`item_user_name_prefix`, `item_name_trgm`, `item_user_recent`, `item_user_created`) + ★`item_user_name_exact (user_id, name_normalized, created_at, id) WHERE deleted_at IS NULL` cho exact lookup; ★`item_purge_idx (deleted_at) WHERE deleted_at IS NOT NULL` |
| `tag` | `id`, `user_id`, `display` 1–50, `normalized` 1–50, `tag_unaccent`, `item_count`, `last_used_at`, `created_at`, `updated_at`, `deleted_at` | `tag_user_norm_uq (user_id, normalized) WHERE deleted_at IS NULL`; ★`tag_purge_idx` |
| `item_tag` | `item_id`, `tag_id`, `created_at` | PK `(item_id, tag_id)`; FK cascade; giữ nguyên khi item/tag soft-delete (mục 2.8) |
| `entry` | `id uuid PK` (client sinh, không default), `user_id`, `item_id`, `type` (CHECK 5 giá trị, API chỉ nhận `text`/`json`), `position int`, `envelope jsonb`, `ciphertext bytea ≤ 263168`, `plaintext_len_bucket int ≤ 262144`, ★`version int NOT NULL DEFAULT 1`, `created_at`, `updated_at`, `deleted_at`, ★`deleted_via text CHECK (deleted_via IN ('entry','item'))`, ★`delete_batch uuid` | ★CHECK `plaintext_len_bucket % 256 = 0 AND plaintext_len_bucket >= 256`; ★CHECK `(deleted_at IS NULL) = (deleted_via IS NULL)`; index §8 + ★`entry_user_changes_idx (user_id, updated_at, id)` **không** điều kiện `deleted_at` (feed cần tombstone); ★`entry_item_live_pos_idx (item_id, position, id) WHERE deleted_at IS NULL` thay `entry_item_pos_idx` |

- `entry.user_id` khớp `item.user_id`: kiểm trong handler (query luôn kèm `user_id`) **và** bằng FK composite ★`FOREIGN KEY (user_id, item_id) REFERENCES item(user_id, id) ON DELETE CASCADE` (dựa trên `UNIQUE (user_id, id)` đã có của §8), thay cho FK đơn `item_id`. `item_tag` không có `user_id`; handler luôn join qua `item.user_id` và `tag.user_id`, và assign kiểm cả hai cùng user dưới lock.
- `entry_count` = số entry **sống** (`deleted_at IS NULL`) của item. `tag.item_count` = số item **sống** có tag đó qua `item_tag`. Số tag sống của một item (trần 20) không có cột counter: đếm `item_tag ⨝ tag` (≤ 20 hàng) dưới lock của item.
- `updated_at` của entry đổi trên **mọi** thay đổi (tạo, sửa body, reorder, xoá, restore) bằng `clock_timestamp()` để feed thấy (mục 2.9). `version` của entry chỉ tăng khi **body** đổi (`PUT`); reorder/xoá/restore không tăng, nên reorder ở thiết bị A không làm thiết bị B đang sửa nhận 412.
- `version` của item tăng khi `name` hoặc `hint` đổi (PATCH). Gán/gỡ tag không tăng (thao tác cộng dồn, mục 2.7).
- Migration forward-only; `0006_content.down.sql` chỉ cho dev. Không đổi bảng P02/P03.

### 2.2 Chuẩn hoá name/tag

Một hàm duy nhất phía Go `internal/textnorm.Normalize(s string) (string, error)` (dùng `golang.org/x/text/unicode/norm`, đã có trong `go.mod`), áp cho `item.name_normalized`, `tag.normalized`, lookup và lọc `q`:

1. Từ chối chuỗi không phải UTF-8 hợp lệ, có ký tự điều khiển C0/C1 (trừ space), ký tự bidi override (U+202A–U+202E, U+2066–U+2069), hoặc rỗng sau trim (`name_invalid` / `tag_display_invalid`).
2. NFC → lowercase Unicode (`unicode.ToLower` theo từng rune; ghi rõ không dùng special-casing theo locale) → thay mọi chuỗi ký tự `White_Space` bằng một space → trim → bỏ ký tự thuộc category `P*` ở **đầu và cuối** (lặp tới khi hết). Giữ dấu tiếng Việt (`mã` ≠ `ma`).
3. Kết quả rỗng (ví dụ name `"!!!"`) → từ chối `name_invalid` (Q12). Độ dài đếm theo rune, kiểm trên cả `name`/`display` gốc (sau trim) và kết quả normalize.

Fixture dùng chung `packages/content-fixtures/normalize.json` (input → normalized hoặc mã lỗi): khoảng trắng Unicode/NBSP, tab, NFD vs NFC, `İ`/`ẞ`/`Σ` cuối từ, dấu câu đầu/cuối và giữa (`c++`, `wi-fi`, `"wifi"`), emoji, chỉ dấu câu, 200/201 rune, ký tự bidi. Web không tự normalize để quyết định danh tính; nếu UI cần so (ví dụ highlight tag trùng trong chip input) thì gọi server hoặc dùng bản TS chạy cùng fixture.

### 2.3 Giới hạn

| Giới hạn | Giá trị | Nơi chặn | Lỗi |
|---|---|---|---|
| `name` | 1–200 rune | client + server | `400 name_invalid` |
| `hint` | 0–120 rune, `null` xoá | client + server | `400 hint_invalid` |
| `tag.display` | 1–50 rune | client + server | `400 tag_display_invalid` |
| Tag sống / item | 20 | server dưới lock item | `409 item_tag_limit` |
| Entry sống / item | 200 | server dưới lock item | `409 item_entry_limit` |
| Plaintext / entry | 262144 B UTF-8 | client trước seal (đo bằng `TextEncoder` trên text cuối cùng) | chặn UI; server dùng hai trần dưới |
| `plaintext_len_bucket` | bội số 256, 256…262144, **bằng** `ceil((octet_length(ciphertext) − 16) / 256) × 256` | server | `400 entry_invalid` |
| `ciphertext` | 17…263168 B (≥ 1 byte plaintext + tag) | server + CHECK DB | `413 entry_too_large` khi > 263168; `400 entry_invalid` khi < 17 |
| Request body entry | ≤ 400 KiB (`ContentEntryJSONLimit`); request item/tag ≤ 16 KiB | server decode | `413 entry_too_large` / `400 invalid_request` |
| `filename` (import) | không nhận (Q7) | — | — |
| Pagination | `limit` 1…100, mặc định 50; entries 1…50, mặc định 20 | server | `400 invalid_request` |

Ghi chú A12: `plaintext_len_bucket` làm tròn lên 256 nên không nói độ dài thật, **nhưng** độ dài ciphertext = độ dài plaintext + 16, nên server vẫn suy ra được độ dài chính xác từ ciphertext. Đây là giới hạn đã biết của envelope v1 không padding (§5.5, threat model); P04 ghi rõ trong threat model và privacy copy, không hứa che kích thước (Q11). Server kiểm bucket khớp ciphertext để metadata không thể bị client đặt sai.

### 2.4 Concurrency: If-Match theo version

- `PUT /entries/{id}` bắt buộc `If-Match: "<version>"` (strong tag, số thập phân không có số 0 đứng đầu) với `version` của entry trả trong mọi response entry. `PATCH /items/{id}` bắt buộc `If-Match: "<version>"` của item. Thay cho `If-Match: updated_at` của §3.7/§9.2 (Q1): timestamp không phải validator đáng tin (độ chính xác serialize, hai thay đổi trong cùng micro-giây, reorder đổi `updated_at`).
- Parser: `httpx.RequireIfMatch` (đã có) → helper mới `httpx.ParseVersionIfMatch(tag) (int32, bool)`; thiếu, `*`, weak, danh sách hoặc sai dạng → `428 precondition_required`.
- Handler khoá hàng (`SELECT … FOR UPDATE`) rồi mới so: không tồn tại/không thuộc user/đã xoá → `404 not_found` (ưu tiên hơn 412); lệch → `412 version_mismatch` kèm `current_version` (dùng lại extension P03). Thành công → `version + 1`.
- Không có last-write-wins cho body: client không bao giờ tự lấy version mới rồi ghi đè; chỉ ghi đè khi người dùng chọn "Giữ bản của tôi" (mục 2.10).

### 2.5 Idempotency, rate limit và thứ tự middleware

- **Mọi** route ghi của P04 (bảng mục 3, cột `I`) bắt buộc `Idempotency-Key` và đi qua `ChainIdempotencyMiddleware` với `IdempotencyRouteConfig{…, RateLimit: LimitUser(limiter, ScopeContentWrite), RequireIfMatch: <route có M>, AllowEmptyDelete: true}` (Q4). Lý do: `PUT` có If-Match, nếu mất response mà retry không có idempotency thì bản ghi của chính mình trả 412; `DELETE`/restore/reorder/assign retry cũng cần trả đúng response gốc. Một quy tắc cho mọi mutation giúp client chỉ có một helper.
- Scope mới `content_write`: **10 request / 1 giây / user**, cửa sổ trượt trên `rate_event` như P03 (§9.1 "write chung 10 rps"). Thêm vào `DefaultUserLimitRules()`; `MaxRateLimitWindow` giữ 15 phút. Replay idempotent và request bị từ chối trước bước 4 không bị đếm (P03 mục 2.3). Vượt → `429 rate_limited` + `Retry-After`; vì request bị chặn trước `Claim`, retry cùng key sau `Retry-After` chạy đúng một lần (A11).
- Không có route P04 nào cần grant re-auth (`A`) hay kill switch `K` của vault.
- Transaction mutation luôn qua `BeginMutationTx` và kết thúc bằng `CommitIdempotencyTx`; lỗi `40P01` (deadlock) và `55P03` (lock timeout) map thành `503 dependency_unavailable` + `Retry-After: 1`; claim được release (chưa commit) nên retry cùng key chạy lại.
- **Thứ tự khoá toàn cục** (chống deadlock, mọi handler và reset hook theo đúng thứ tự, bỏ bước không cần): `vault` (`FOR SHARE` cho entry, `FOR UPDATE` cho reset) → các hàng `item` (sắp theo `id`) → các hàng `tag` (sắp theo `id`) → hàng `entry`. Tag restore phải đọc danh sách item trước (không khoá), khoá item theo thứ tự, rồi mới khoá tag và kiểm lại.

### 2.6 Entry: envelope, khoá và kích thước

- Request tạo: `{id, type, envelope, ciphertext, plaintext_len_bucket}` (+ `source` cho import). Server: `ValidateEntryID(id)`; `type ∈ {text, json}` (import ép `json`); `ValidateEntryEnvelope` trên **byte thô** của field `envelope` (giữ `json.RawMessage` khi decode request để phát hiện key trùng trước map); decode base64url strict `ciphertext`; kiểm giới hạn mục 2.3.
- **Khoá hiện tại:** trong transaction, `SELECT vault_key_id FROM vault WHERE user_id=$u FOR SHARE` trước mọi khoá khác. Không có vault → `404 vault_absent`. `envelope.key_id ≠ vault_key_id` → `409 entry_key_mismatch`. Vì reset khoá `vault FOR UPDATE` rồi mới xoá, request ghi cũ bay song song với reset hoặc chạy sau reset luôn bị chặn bởi bước này (A9 "stale writes fail"). `key_id` dạng `sk:` (đã cho phép ở validator P03 cho P08) bị từ chối ở MVP vì không bằng `vault_key_id`.
- **PUT:** body `{envelope, ciphertext, plaintext_len_bucket}`; `id` trên path, `type` không đổi được (gửi `type` → `400 invalid_request`); nonce mới phải khác nonce đang lưu (`400 entry_nonce_reused`, kiểm rẻ chống client lỗi dùng lại nonce); cùng kiểm khoá như trên.
- **ID do client:** `entry.id` đã tồn tại (của user này hoặc user khác, sống hay đã xoá) với request khác → `409 entry_id_conflict`, không lộ chủ sở hữu; retry cùng key được middleware trả response gốc trước khi tới handler.
- **Client:** sinh `entry_id = crypto.randomUUID()` **một lần**, đo byte UTF-8, gọi `sealEntry({ entryId, keyId: vaultMeta.vault_key_id, plaintext, opGeneration })` một lần, tính `plaintext_len_bucket = ceil(bytes/256)*256` (bytes ≥ 1), giữ nguyên byte body JSON + `Idempotency-Key` tới khi nhận 2xx hoặc 4xx xác định. Không seal lại dưới cùng key. Text rỗng (0 byte) không lưu được: nút Lưu disabled.
- **Mở:** trước `openEntry`, caller so `envelope.key_id` với `vaultMeta.vault_key_id`; lệch → hiện "entry này mã hoá bằng khoá cũ" (không gọi Worker); AEAD fail → card "Không giải mã được" (§7.7). Ánh xạ lỗi entry riêng, **không** dùng `classifyCryptoError` của unlock (vốn map `AEAD_DECRYPT_FAILED` thành "sai passphrase").

### 2.7 Item, tag và quan hệ

- `POST /items {id?, name, hint?}` luôn tạo mới (không upsert theo name; §9.2). Client gửi `id` UUID v4 trong quick-add để retry nhiều bước không tạo bản sao; `id` đã tồn tại với payload khác → `409 item_id_conflict`.
- **Exact lookup** `GET /items/lookup?name=&cursor&limit` (★mới): server normalize `name`, trả **mọi** item sống có `name_normalized` bằng đúng giá trị đó: `{items:[ItemSummary], total, next_cursor}` sắp `created_at DESC, id`, `total` là `count(*)` chính xác trong cùng snapshot. Không dùng `/suggest` top-K. Rỗng → `{items:[], total:0}`.
- `ItemSummary = {id, name, hint, tags:[{id, display}], entry_count, version, created_at, updated_at, last_used_at}`; `tags` tối đa 20, sắp theo `display`.
- `GET /items?tag_id&q&cursor&limit&sort=recent|alpha|created`: `q` là prefix trên `name_normalized` (index `text_pattern_ops`), escape `%`/`_`; fuzzy thuộc P05. Cursor keyset theo cột sort + `id`, mã hoá base64url opaque, gắn `sort`/`tag_id`/`q` (cursor lệch tham số → `400 invalid_request`).
- **Tag:** `POST /tags {display}` upsert theo `normalized` trong số tag sống: có rồi → `200` + tag hiện có (không đổi `display`); chưa có → `201`. Hai upsert song song cùng normalized: `INSERT … ON CONFLICT (user_id, normalized) WHERE deleted_at IS NULL DO NOTHING RETURNING *` (suy luận partial unique index `tag_user_norm_uq`); không có dòng trả về → `SELECT` tag sống đó và trả `200`. `PATCH /tags/{id} {display}` đổi display; normalized trùng tag sống khác → `409 tag_conflict` (snake_case thay `TAG_CONFLICT` của §2.4/§9.2).
- **Gán tag là cộng dồn** (Q3): `POST /items/{id}/tags {tag_ids:[…]}` (1…20 phần tử, không trùng) thêm các cặp chưa có (`ON CONFLICT DO NOTHING`), kiểm mọi `tag_id` là tag sống của cùng user (sai → `404 not_found` cho cả request, không ghi gì), kiểm tổng tag sống ≤ 20 sau hợp, cập nhật `tag.item_count` và `last_used_at`. Response `{item: ItemSummary, added_tag_ids}` (`added_tag_ids` = cặp thật sự mới thêm, để Undo quick-add chỉ gỡ đúng cặp mình thêm). `DELETE /items/{id}/tags/{tag_id}` gỡ một cặp, trả `ItemSummary` (gỡ cặp không có → vẫn 200, không đổi gì). **Bỏ** `PUT /items/{id}/tags` (thay toàn bộ) khỏi MVP vì đó là ghi đè snapshot — đúng điều phase doc cấm; Task 1 xoá khỏi §9.2.
- Response mọi mutation item/tag trả trạng thái mới để client cập nhật cache, không đoán.

### 2.8 Xoá, restore, provenance và purge

| Hành động | Server làm (một transaction, thứ tự khoá mục 2.5) | Undo |
|---|---|---|
| `DELETE /entries/{id}` | `deleted_at = clock_timestamp()`, `deleted_via='entry'`, `entry_count − 1` | `POST /entries/{id}/restore` |
| `DELETE /items/{id}` (`?only_if_empty=true` tuỳ chọn) | sinh `delete_batch`; item `deleted_at` + `delete_batch`; mọi entry **sống** của item → `deleted_via='item'`, cùng `delete_batch`; `entry_count = 0`; `item_count − 1` trên mọi tag sống của item; `item_tag` **giữ nguyên**. Với `only_if_empty`: còn entry sống → `409 item_not_empty`, không đổi gì | `POST /items/{id}/restore` |
| `DELETE /tags/{id}` (`?only_if_unused=true` tuỳ chọn) | tag `deleted_at`; `item_tag` giữ nguyên nhưng không còn tính vào tag sống của item; với `only_if_unused`: `item_count > 0` → `409 tag_in_use` | `POST /tags/{id}/restore` |
| `POST /entries/{id}/restore` | entry phải `deleted_via='entry'` (`'item'` → `409 entry_restore_via_item`: restore item thay vì entry); item sống (`409 item_deleted`); `entry_count < 200` (`409 item_entry_limit`); giữ nguyên `position` cũ để entry về đúng chỗ | — |
| `POST /items/{id}/restore` | khôi phục item và **chỉ** entry có `deleted_via='item' AND delete_batch = item.delete_batch`; entry user đã xoá riêng trước đó vẫn xoá (không resurrect, A8); `item_count + 1` cho tag sống; kiểm trần 200 (luôn đúng vì item xoá thì không thêm entry được, vẫn kiểm) | — |
| `POST /tags/{id}/restore` | `normalized` đã bị tag sống khác chiếm → `409 tag_conflict`; mọi item sống gắn tag phải còn < 20 tag sống, không thì `409 item_tag_limit` và không restore gì (không restore một phần) | — |

- Restore/xoá lặp lại (đối tượng đã ở trạng thái đích) → `200`/`204` như lần đầu, không đổi gì (ngoài replay idempotent).
- Entry/item/tag đã soft-delete không xuất hiện ở list/lookup/get (404), trừ feed (mục 2.9) và restore.
- **Purge** (job River mới `content_purge`, mỗi giờ, theo lô 500 như `idempotency_prune`): entry `deleted_at < now() − 30 days`; item `deleted_at < now() − 30 days` (cascade entry, `item_tag`); tag `deleted_at < now() − 30 days` (cascade `item_tag`). Idempotent, chạy lại an toàn; không đụng hàng sống.
- **Undo phía UI** (§3.4, §3.8): toast 5 giây gọi đúng endpoint restore/delete của mutation đích; Undo là một mutation mới với `Idempotency-Key` mới; quá 5 giây không còn nút (API restore vẫn dùng được 30 ngày, nhưng P04 không có màn thùng rác — Q9).

### 2.9 Feed thay đổi entry

- `GET /entries/changes?since=<RFC3339Nano>&cursor&limit` (limit 1…200, mặc định 100) trả `{changes:[EntryChange], next_cursor, watermark}`; `EntryChange = {id, item_id, type, position, version, plaintext_len_bucket, created_at, updated_at, deleted_at}` (**không** có envelope/ciphertext; client tải body khi cần). Gồm tombstone (`deleted_at` khác null). Sắp `(updated_at, id)`, cursor keyset trên đúng cặp này nên hai hàng cùng `updated_at` không bị mất ở biên trang.
- `watermark` = `now()` của server ở đầu request đầu tiên của chuỗi trang (gắn trong cursor). Client lưu `watermark` và lần sau gửi `since = watermark − 120 s` (vùng chồng lấn lớn hơn thời gian một transaction ghi có thể kéo dài giữa lúc đặt `updated_at` và COMMIT), rồi dedup theo `(id, updated_at)`. Đây là "best effort delta", không phải sync bền vững: client vẫn refetch nguồn chuẩn (list item đang mở) khi focus/reconnect (phase doc).
- `since` cũ hơn `now() − 29 days` (tombstone có thể đã purge) → `410 changes_window_expired`; client bỏ watermark, refetch toàn bộ danh sách đang hiển thị. `since` sai dạng → `400 invalid_request`.
- Item/tag không có feed: client refetch list item/tag khi focus/reconnect (React Query `refetchOnWindowFocus: true` riêng cho key content). Cursor bền và SSE là P07-A.

### 2.10 Client: cache, lock, draft, retry

- **Query key** (namespace mới, một chỗ khai báo `features/items/query-keys.ts`): `['content','items',{sort,tagId,q}]`, `['content','item',id]`, `['content','lookup',normalizedName]`, `['content','tags',{sort}]`, `['content','entries',itemId]` (metadata + envelope + ciphertext, không plaintext), body plaintext **chỉ** dưới `vaultBodyQueryKey(entryId, version)`. Không key nào khác chứa plaintext; cấm ghi plaintext vào `queryClient.setQueryData` ngoài namespace body (rule review + test quét cache).
- **Lock** (P03 đã xoá `['vault','body']`): P04 đăng ký `registerSecretFormReset` cho mọi editor text/JSON, ô body quick-add, ô import và state bảng JSON đang sửa, đánh dấu các `textarea` chứa body bằng `data-vault-secret`. Lock **bỏ draft chưa lưu** (Q15); sau unlock hiện một dòng "Bản nháp chưa lưu đã bị xoá khi khoá vault". Không tự gửi lại sau unlock.
- **Reset vault:** khi `vault_key_id` trong `vaultMeta` đổi hoặc vault absent (P03 đã broadcast `vault_changed`), client `removeQueries({queryKey:['content','entries']})` và xoá watermark feed; item/tag giữ nguyên. Copy dialog reset (`features/settings/security/vault/reset-vault-dialog.tsx`) nói rõ "xoá toàn bộ entry, giữ mục và tag" (**kiểm sau merge P03** copy hiện tại).
- **Retry mutation:** helper duy nhất `lib/api/content.ts` `contentMutate({method, path, body, idempotencyKey, ifMatch?})` serialize body **một lần** thành chuỗi, giữ nguyên chuỗi + key qua retry; tự retry tối đa 2 lần với lỗi mạng/timeout, `409 idempotency_in_progress` (chờ 1 giây), `429` (chờ `Retry-After`), `503 dependency_unavailable`; mọi lỗi 4xx khác trả về UI. Mutation không retry vô hạn, không queue offline (§7.7); offline → giữ draft trong memory của phiên + banner.
- **Conflict (412):** card giữ draft, hiện "Đã được sửa ở thiết bị khác" với hai nút: **Tải bản mới** (bỏ draft sau một xác nhận inline) và **Giữ bản của tôi** (tải version mới nhất, seal lại draft với nonce mới, `PUT` với `If-Match` mới, `Idempotency-Key` mới). Không có màn so sánh (Q11 cụm UX).

### 2.11 Quick-add

**Grammar** (`apps/web/features/omnibox/quick-add-parse.ts`, fixture `packages/content-fixtures/quick-add.json`):

1. Chỉ dòng đầu chứa phần đầu (`head`). Tìm `:` đầu tiên trên dòng đầu **không** đứng ngay trước `//` (theo §3.4 `(?!//)`); không có → chế độ tìm kiếm. Input bắt đầu bằng `#` → chế độ lọc tag, không phải add.
2. `body` = mọi thứ sau `:` (kể cả các dòng sau), bỏ khoảng trắng đầu và cuối, giữ nguyên khoảng trắng/xuống dòng ở giữa. `body` rỗng → chưa phải add mode (hiện gợi ý "Gõ nội dung sau dấu :").
3. `head` = phần name rồi các token tag. Token tag bắt đầu `#`, kết thúc ở khoảng trắng, không chứa `#`/`:`. Sau token tag đầu tiên, mọi token phải là tag; có chữ thường xen giữa → add preview báo "Tag không có khoảng trắng; dùng chip để gắn tag có khoảng trắng" và Enter bị chặn (Q5). Name rỗng → không add.
4. `:` không có khoảng trắng sau vẫn hợp lệ (`wifi:Abc123` → name `wifi`); trường hợp như `10:30 họp` vẫn thành add với name `10` — preview "Sẽ lưu vào …" hiện trước Enter nên người dùng thấy (Q13).
5. Body là JSON hợp lệ (parser Task 12, chỉ khi bắt đầu bằng `{` hoặc `[`) → banner "Phát hiện JSON — Lưu như bảng" mở import (Task 17) với text đó; không tự đổi type.

Fixture tối thiểu: URL trong body (`link: https://a.b/c`), URL trong name (`docs https://a.b: ghi chú`), `a::b`, `:abc`, `abc:`, nhiều dòng, CRLF, tab, full-width colon `：` (không phải dấu tách), tag tiếng Việt, `#` một mình, tag 50/51 rune, name 200/201 rune, khoảng trắng Unicode.

**Không lộ body:** khi parse ra add mode, mọi request phát từ omnibox (lookup, list `q`) chỉ dùng `name`; request đang bay từ lúc còn ở chế độ tìm kiếm bị `AbortController` huỷ ngay khi chuyển add mode, và debounce cũ bị huỷ. Test network capture: không request nào (URL, header, body) chứa chuỗi body, trừ ciphertext.

**Luồng lưu** (một "kế hoạch quick-add" giữ trong memory của phiên, không persist):

1. Parse → lookup `GET /items/lookup?name=` (debounce 150 ms trong add mode, chỉ name). 0 → sẽ tạo mới; 1 → append; ≥2 → Enter mở picker (U9): mỗi dòng name + tối đa 3 chip tag + `created_at` + `entry_count`, phân trang "Xem thêm" nếu `total > items.length`, cuối list "Tạo mục mới cùng tên". Picker trả **item ID**, không trả chuỗi. `Ctrl+Enter` luôn tạo mục mới (§3.4).
2. Khi Enter (vault phải unlocked; locked → nút "Mở khoá để lưu", draft giữ trong ô tới khi lock xoá): dựng kế hoạch: `itemId` (UUID mới nếu tạo), danh sách tag cần upsert, `entryId`, seal **một lần**, mỗi bước một `Idempotency-Key` sinh trước.
3. Thực hiện tuần tự: `POST /items {id: itemId, name}` (nếu tạo) → `POST /tags` cho từng tag (upsert) → `POST /items/{id}/tags {tag_ids}` (cộng dồn) → `POST /items/{id}/entries`. Bước lỗi giữ draft + kế hoạch; "Thử lại" chạy tiếp từ bước lỗi với đúng key/byte cũ, nên timeout ở bất kỳ bước nào không tạo bản sao (A3). Toast "Đã lưu vào **name**" chỉ hiện sau khi entry commit (201).
4. Undo 5 giây (toast): `DELETE /entries/{entryId}`; nếu kế hoạch đã **tạo** item thì tiếp `DELETE /items/{itemId}?only_if_empty=true`; với tag kế hoạch đã **tạo mới** (POST trả 201) thì `DELETE /tags/{id}?only_if_unused=true` sau khi gỡ cặp gán. `409 item_not_empty`/`tag_in_use` = thiết bị khác đã dùng → giữ lại, không báo lỗi. Tag có sẵn trước đó thì chỉ gỡ cặp gán do kế hoạch thêm (`DELETE /items/{id}/tags/{tag_id}`) nếu cặp đó **mới** (response assign cho biết cặp nào mới thêm: `added_tag_ids`). Copy toast nói rõ phạm vi: "Hoàn tác: xoá nội dung vừa lưu (và mục/tag vừa tạo nếu còn trống)".

## 3. Endpoint và operationId

Path tương đối `/api/v1`. `S` session, `C` Origin + CSRF, `I` `Idempotency-Key`, `R` rate limit `content_write`, `M` `If-Match: "<version>"`. Mọi route kiểm ownership theo `user_id` của principal; ID của user khác trả như không tồn tại (`404 not_found`). Bảng này là contract cho OpenAPI; Task 1 sửa §9.2 cho khớp.

| Method / path | operationId | Điều kiện / response |
|---|---|---|
| `GET /items` | `itemsList` | S; `?tag_id&q&cursor&limit&sort`; 200 `{items:[ItemSummary], next_cursor}` |

| Code | HTTP | Khi nào |
|---|---|---|
